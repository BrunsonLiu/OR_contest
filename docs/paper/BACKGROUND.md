# 背景草案：门店拣货中的顾客确认

本文对应论文第一节。它只写现实流程和决策困难，不提前给结论；证据边界写在最后。

## 1.1 业务场景

生鲜电商和即时零售把订单履约放到了门店：顾客在线下单，门店拣货员按清单在货架间取货，拣完后交接给骑手或顾客。生鲜订单时效紧、商品会缺货，门店不可能为每一单预先确认全部商品。

当拣货员走到货架发现缺货时，常见做法是提出一个替代品，让顾客在手机页面上同意、拒绝或另选。这个确认不是在订单创建时完成的，而是在拣货执行中产生的；顾客的回复也不一定马上到。

## 1.2 确认的实际流程

以 Instacart Connect 的公开接口文档为例，可以把流程拆成四个可核实的事实：

1. **商品处理状态与顾客决定分开记录。** 商品有“未拣、已找到、已替换、待退款”等状态，替代品另有“待回复、已同意、已拒绝”的替代状态；两者可以同时存在。接口文档明确说，替代状态 `PENDING` 只表示“已提出、顾客尚未回复”。
2. **拒绝可以改变后续任务。** 顾客拒绝时，接口允许提供一个替代商品，系统提示拣货员去寻找；也就是说，回复会生成一条新的取货任务，而不是只改一个字段。
3. **确认有可执行窗口。** 该接口的前置条件是订单处于 `picking`、商品处于 `REPLACED` 且替代状态为 `PENDING`；订单离开拣货状态后，同一变更不能再修改（错误码 `4001` “no longer modifiable”），同一变更也只能被回复一次。
4. **回复到达前不能算已拣。** 处理标记不等于顾客同意，也不等于商品已入筐；拣货员在回复前不能把替代品当作已完成。

这些事实来自同一平台的官方文档，不是跨平台拼接。它们足以支持“回复会生成/取消任务、窗口随订单状态关闭”这一流程，但不提供回复时延分布、未回复时的默认动作，也不说明谁有权结束拣货。

## 1.3 为什么是决策问题

拣货员在缺货点面临的不只是“换哪个商品”，还有一串与时间有关的决定：

- 是现在提出替代，还是先把其它商品拣完再回来提出？
- 等待回复时，是原地等，还是继续拣别的商品？
- 回复到达后，是否值得折返取替代品，还是放弃这一项？
- 订单什么时候结束拣货，直接决定确认窗口什么时候关闭。

这些决定相互影响：请求发得早，回复更可能来得及执行，但可能更早暴露替代品、增加折返；继续拣货能利用等待时间，但可能错过窗口。替代品是否在现有路线上，会改变折返成本；回复是否被拒绝，会改变后续任务。

## 1.4 研究范围

本文先限定一个门店、一名拣货员、一张已承诺订单，给定交接截止和确认窗口；不加入多仓、车辆路径、顾客偏好学习。多订单共享库存、多个拣货员和动态定价留到后续。

生鲜属性在本文中只作为场景背景：商品会缺货、替代需要顾客确认、订单有时效。模型不额外加入温控或腐败约束；若后续要用冷链特性，必须证明它改变决策，而不是给标题加词。

## 1.5 证据边界

- 平台文档是公开接口说明，不是企业运营数据；它证明接口支持哪些状态和操作，不证明这些操作的发生频率或经济价值。
- 没有真实回复日志、返拣记录和窗口规则；文中所有时延、拒绝概率和截止参数都是情景参数。
- 未回复时的默认动作、结束拣货权限、实际回复与返拣时间仍缺证据；在这些补齐前，结论只能是条件性的。
- 不同平台的规则不能拼接成同一流程；本文以 Instacart Connect 的同一套文档为主，其它平台只作对照。
