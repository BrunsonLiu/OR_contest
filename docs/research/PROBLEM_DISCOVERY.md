# 论文研究设计与问题发现

更新日期：2026-10-27。2026-10-27 完成顾客确认候选的第二轮逐篇对照（新增门店随机同步等待与动态订单重优化两项正文），并补入一页问题定义、四项检查与判别实例；结论为“差异待检验”，业务参数仍缺。论文目标按用户明确的三项要求组织：新问题、针对该问题改进经典算法、实验验证及有条件的实践启示。尚未确定论文选题或算法。本页是现行研究设计与候选证据入口，持续修订，不按轮次新增总结报告。

## 整改后的论文主线

论文需要建立一条可核查的论证链：现实中发生了什么新的决策困难 → 哪个必要机制改变了决策 → 模型如何表达这个机制 → 经典算法在何处需要改进 → 实验怎样区分机制价值和算法贡献 → 哪类决策者在什么条件下可以采用建议。

工程记录保证过程可追溯，不替代上述学术贡献。现有竞赛解答保留为基础材料；不将增加约束、替换预测器、调用求解器或换一个应用名称直接列为论文贡献。

### 三项贡献及当前缺口

| 要求 | 需要交付的实质内容 | 当前判断 |
| --- | --- | --- |
| 新的问题 | 一页问题定义：主体、对象、信息到达顺序、可选行动、不可逆节点、完成条件；与最近邻具体模型逐项比较，说明有现实意义的决策关系及现有研究的覆盖范围 | 待核查。顾客确认候选已把剩余差异收窄为“执行中回复生成/取消任务 + 窗口随订单状态关闭”，四项检查完成一轮；仍缺业务参数，也尚未确认足以独立立项的问题。未完成核查不等于已被证明重复 |
| 针对问题改进经典算法 | 选定一个有出处的经典框架，说明原算法如何适配新问题、哪里失效或低效、改动怎样处理核心机制；保留公平的原算法对照 | 未开始。先确定问题结构，再选经典框架；DFL 暂无默认地位 |
| 实验与实践价值 | 小规模正确性证据、同预算算法比较、机制与算法两类消融、规模与边界分析；建议须落到可操作变量并说明适用条件 | 新研究线未开始。已有竞赛实验不能直接变成新问题的验证 |

“新问题”允许属于 LRP、库存、调度等已有大类。是否能写成某个通用数学规划、MDP，或是否含有经典问题作为特例，都不能单独判断原创性。需要核对的是最接近的具体问题定义、已有结论和方法适用范围；如果只改场景名称或常规参数，当前项目不据此立项。

### 逐篇寻找具体差异，避免按问题大类排除

2026-10-25 根据用户纠正修订筛选口径：过去“已筛掉的宽泛方向”等表述容易把局部重复扩大为整个方向没有研究空间，撤回这种推断。冷链仍为当前研究范围；不要求跳出冷链或所有经典问题大类才能提出新问题，也不因找到一个相近关键词就改换场景。

每个优先候选围绕最接近的具体论文建立对照，至少核对以下内容；每项注明正文位置或“尚未读到”，不把未读到写成文献没有。

| 比较维度 | 要查清的细节 | 差异的实质检验 |
| --- | --- | --- |
| 决策对象和状态 | 批次/订单是否区分；品质按时间、处理历史还是其他状态变化 | 差别是否只需换单位或重估常数，还是会改变库存可替代性、行动排序或可接受交付 |
| 信息和时间顺序 | 何时获知需求、品质、处理结果；先承诺还是先观察；哪些决定不能撤回 | 原文的政策能否用当前可得信息执行；是否存在尚未揭示结果下必须作出的不同选择 |
| 行动和资源 | 哪些量固定、哪些可控制；资源是否由多个批次共同占用 | 差异是否改变可选行动及跨批次机会成本，而非仅增加一项费用名称 |
| 机制之间的关系 | 一个行动是否影响另一个环节的可行性、收益或状态转移 | 能否分开处理；联合关系是否已经在该文或其最近邻中研究过 |
| 目标、结论与方法 | 评价终点、服务条件、定理假设、算法适用范围及已做实验 | 即便通用模型能够表达，新关系是否仍需要不同性质、算法处理或验证；不以可表达性替代覆盖判断 |

对照结果分别标为“该部分已覆盖”“差异待检验”或“证据不足”。只有完整决策关系及所主张贡献确已被覆盖，才以重复为由撤回该项主张。因为业务依据不足或偏离当前范围而暂停，另写原因，不包装成学术上无价值。

细节差异可以成为研究起点。需要说明它为什么在现实中出现、如何影响决策，以及已有结论能否直接沿用；不要求每项差异都成为新变量，也不预设增加一个约束就足够。冻结机制和最小实例用于识别影响，不要求候选必须让经典模型完全无法表达，也不把缺少反例直接判为无价值。下一步先沿冷链范围完成具体比较，再决定是否收窄对象。

### 先检查问题与模型是否真正结合

候选进入算法研发前，至少完成以下四项检查。它们是本项目的研究选择标准，不是关于论文录用的保证。

1. **删去行业名称后，问题还剩什么？** 写出完整决策过程，说明特殊性来自哪里。若新机制本来适用于即时零售等更广场景，应按实际范围定位；不为突出“生鲜”而人为加入温控、腐败或多仓约束。
2. **冻结核心机制后，决策是否改变？** 明确冻结的是哪项状态转移、信息到达或行动权限。比较它是否改变可行策略、目标含义或最优政策，不能只指出参数数值变了。仍需查文献，不能把机制有影响等同于新颖性成立。
3. **构造一个能手工核对的判别实例。** 检查差异是否改变合法行动、行动排序、资源分配或评价结果；也可检查已有性质在什么条件下仍成立。若旧模型可以直接表达，应如实承认，并继续比较已有研究是否处理了该关系及其后果；无需为了赢比较而限制它。计算实验仍须通过 `run.py` 留证。
4. **现实机制—数学表达—算法部件—实验观察逐项对应。** 模型中新增的状态、变量、约束或目标项必须有业务理由；算法中的新增部件必须处理其中的具体困难；实验必须能够单独检验这一作用。未建立对应时，不扩写论文题目或贡献声明。

### 对现有项目和候选的重新定位

| 材料 | 现在的用途 | 不能直接承担的论文贡献 |
| --- | --- | --- |
| 现有问题四仓网模型 | 竞赛问题的已审计实现、固定策略评价基础；可参考数据读取和验证设施 | 代码以开仓、供货分配、调拨和固定配送关系为主，未显式优化车辆访问顺序；不将其直接描述为已实现完整车辆 LRP，也不因预算鲁棒化就宣称新问题。见[现行方法](../methodology/problem4_robust_methodology.md) |
| 记录迟到候选 | 因生鲜业务证据缺失暂停；保留局部对应与尚未核查的关系 | 共享前置条件这一局部机制已知；尚未证明完整随机物流问题已被覆盖 |
| 顾客确认候选 | 问题池中的待核查对象，不再默认优先立项；已有证据可用于检验定义是否成立 | 等待、恢复、途中改单、替代与路径联动均已有前例；核心机制不依赖生鲜，应按即时零售履约定位。剩余差异（回复生成任务 + 窗口关闭）待在更广实例上验证，尚不构成生鲜特有贡献 |
| DFL 与现有预测比较 | 方法备选及竞赛评价材料 | 不能用训练新模型或预测误差下降代替新问题与专门算法贡献 |

当前顾客确认候选只建立了初步对应：回复及订单状态限制 → 待确认状态、任务分支和可执行窗口 → 尚未确定算法部件 → 尚无验证实验。未回复默认动作、结束权限与实际时间仍缺证据。不能因为已投入检索就自动把它升级成论文主线。2026-10-27 的对照进一步显示：Bhowmick 等的门店 MDP 已覆盖随机同步等待、放弃与期限，Lorenz 等已覆盖执行中改派；因此不能再把等待或重路由本身当差异，剩余判断集中在回复是否改变任务集合以及窗口规则。

以这个候选作结合检查：若保留“执行中发出请求、回复改变后续任务”，模型就须表示尚未揭示的任务分支与当前合法行动。把一开始要访问的节点全部固定下来，会遗漏所声称的决策过程；相反，若把全部回复提前揭示并固定结果，就应退化到相应的确定任务拣货问题。这个退化关系可作为实现核查，而不能作为新颖性证明；已有随机路径/调度模型可能已经表达同一关系，仍须逐项比较。若还无法指出既有模型遗漏了什么，问题贡献就未成立。

同样，记录请求时间和检验顾客授权若是任何合法算法都必需的，应放入共同状态/评价器。只有进一步提出了处理该结构的搜索或决策改进，并在共同评价下验证收益，才有算法贡献；不能把基线故意删去这些必要信息，再将恢复信息算作创新。

### 算法改进必须跟随问题结构

选题确定后，先用一个经典框架建立能够合法求解新问题的基线，再针对已识别的困难改进。若保留序贯信息到达，基线不能预知未来；若需要增加状态或可行性检查才能使基线合法，这部分应作为共同适配，不能只给改进算法使用。

只有确认主要困难是路径/组合邻域搜索后，才考虑 LNS/ALNS。例如，[Ropke、Pisinger（2006）](https://doi.org/10.1287/trsc.1050.0135) 已有取送货时间窗 ALNS 框架；采用框架本身不构成改进。若未来确认某类任务存在不可分割的依赖关系，可进一步检验成组移除/插入、依赖可行性修复或增量评价是否必要、有效，并逐一排重和消融。**这只是条件性的算法设计示例，尚未选定 ALNS，也没有声称这些部件新颖。** 若问题以等待与停止决策为主，应另选与该结构相符的经典序贯决策框架，避免为适配 ALNS 把关键机制删掉。

算法贡献应回答：原框架具体损失了什么信息或搜索机会；改动保留了什么；增加了多少计算成本；什么条件下收益消失。单纯换权重、改名称、调参，或叠加多个流行方法，目前不足以满足本项目目标。

### 实验要分别回答四类问题

| 目的 | 必须具备的对照与证据 | 解释边界 |
| --- | --- | --- |
| 模型与实现是否正确 | 手算/独立核算，小实例用精确方法或枚举核对；序贯问题对照须使用相同信息结构。记录解状态、界、gap 和超时 | 知道全部未来的解只能作注明信息优势的界/参考，不能当作可部署政策；完整性检查不证明模型正确 |
| 算法是否有效 | 改进算法对比共同适配后的经典算法及适当的简单策略；相同实例、信息、终止规则、调参机会和实际计算预算 | 同时报可行率、目标/服务表现与耗时；限时未找到解、可行解和证明最优分别处理；没有稳定收益时不宣称改进成功 |
| 贡献到底来自哪里 | **机制消融**：完整机制与冻结机制；**算法消融**：同一完整问题下删除各新增算法部件 | 忽略机制的模型所得方案须放回完整问题评价，违规不能通过低成本掩盖；两类消融不能相互替代 |
| 何时值得实践采用 | 对可控制的规则和外部条件分开做敏感性分析，寻找采用范围、无收益范围及可能的反转 | 没有比较相关行动，就不能给相应建议；参数假设变化下的模拟结果不称为企业实证因果效应 |

在正式比较前确定实例生成规则、关键参数范围、主指标、容差、预算、种子及训练/调参/测试划分；不根据最终结果挑有利区间。随机策略在配对实例上报告效果量与不确定性，不能把同一实例的多次种子运行当成多个独立业务样本。方法选择所见实例不能再称独立测试。

缺少真实数据不自动阻止研究。可采用透明的合成实例和可追溯的公开背景参数，检验机制与算法；必须区分原始赛题数据、公开来源和人为假设。现有 23 天城市/SKU 需求不包含顾客回复、返拣或授权字段，不能据此校准这些过程，也不能替合成订单背书。所有新求解、训练、回测和绘图沿用现有工程与实验标准，不新建平行运行体系。

### 实践启示应能说明行动和适用范围

每条建议至少回答五点：谁采取行动、可以调整什么、依据什么可观测条件、改善什么结果并承担什么代价、在哪些条件下不适用。比如“在何种已验证条件下提前核查某类商品”只能在问题确有该行动、实验比较过相应政策时提出；不能从一条成本下降曲线推出“提高智能化水平”等泛泛建议。

暂不预写正向启示。没有可校准的现场数据时，只给明确参数与假设范围内的机制解释及条件性政策建议，列出部署前还需验证的参数。

### 当前推进顺序

1. 先提交一页候选问题定义和最近邻差异表，并完成上述四项检查；当前候选与新收集候选按同一标准比较，未通过的不进入算法开发。
2. 对通过的问题，建立核心机制的数学表达、独立约束核查和最小实例；确认模型没有丢失导致该问题成立的关系。
3. 选定一个经典算法，完成共同适配的基线，再提出与核心机制一一对应的改进；形成可被消融证伪的算法主张。
4. 锁定比较协议后运行正确性、算法、两类消融、边界与政策实验，保留全部成功与失败记录。
5. 按“新问题—模型—算法改进—验证—条件性实践启示”组织论文。任何一环缺证据，保留为待办，不用其他环节的完成量替代。

## 选题边界

赛题提供生鲜、两级仓网和履约要求等场景素材。研究可补充批次、合同、信息到达过程和其他数据，但新增机制必须有现实证据，并与原赛题解答分开。23 天订单历史限制现有数据上的统计验证，不限定新问题的建模边界。

选题先交代现实机制、决策主体、信息与行动的时间顺序、目标及约束，再核查最接近的问题定义。DFL、鲁棒优化或其他算法在问题通过筛选后选择。研究价值不以是否使用某一种方法衡量。

### 从赛题省略的机制出发

### 一页问题定义草案

**问题：在暂养恢复资源有限、批次生理状态不同且订单存在出运/到货期限的活岩龙虾业务中，如何安排各批次的恢复占用和出运顺序，以控制物流及持有成本，并满足明确声明的存活表现目标？**

- **主体和对象**：先限定一个出口/集货设施及若干批次、若干已知目的地订单，不先做多层选址或车辆串点路线。批次属于同一物种，具有到达时间、可观测状态指标、存活数量及已知处理历史。有限池位/服务能力是待核实和参数化的规划条件，尚无企业容量数据。
- **信息顺序**：批次入场时取得当时能观测的指标；企业选择恢复或出运；后续状态和死亡逐步发生。不能让企业预知最终谁会死亡。具体可观测指标及测量误差尚未定稿，不把全部生理状态假定为可直接观测。
- **行动**：决定哪些批次占用恢复设施、占用时段与时长，以及何时出运、分配给哪个允许的订单。只有找到相应业务依据后才加入拒单、转加工、跨设施转移等行动。
- **评价**：分别记录按时到货量、到货存活量以及到货后预先指定观察期 H 内的存活量。H 和存活目标是研究协议参数，尚非赛题或真实合同要求；评价期间的下游环境必须固定/记录，避免把不同接收条件导致的死亡全归于运输方案。
- **必要机制**：恢复可能降低存活个体的应激，但不能增加已经死亡的数量；运输及搬运的死亡风险可能依赖进入该段时的状态。因此恢复资源分配与出运时点不能在核实关系前简单分别优化。不能预设每次恢复都有净收益，暂养不当或过长也可能有代价。

行业报告提及的恢复以天计，赛题关注的 10 小时时效不能直接照搬。应先明确恢复发生在接单前备货、承诺前准备还是承诺后；若业务不允许在承诺后恢复，就只能使用提前恢复的可售批次。未经证实，不通过延长原赛题的时效口径获得“改进”。

### 最小解析检查：总时长相同，处理顺序可能不同

以下是用于检查定义的条件性数学示意，不是拟合模型、实测结论或新定理，未运行计算实验。用 n 表示存活数量，x 表示假设的可恢复应激状态。设一段恢复将 x 变为 r(x)，不增加 n；同一运输段的存活比例为 p(x)。在“r(x)≤x，p 随 x 非增，且该恢复段本身无死亡”的限定下，恢复后运输得到 n·p(r(x))，先运输再恢复仅剩 n·p(x)。若存在严格差异，则相同的运输段与恢复时长无法只用总耗时的一个损耗值表达；后做恢复也不能补回先前死亡。

这里的零恢复死亡和标量 x 都是示意假设，不能用于正式实验或生理参数校准。实际恢复有死亡时，还需计入对应的存活转移；多维指标未必可以合成单一“应激分数”。该例只显示需要验证的关系，**不证明经典状态依赖库存/调度模型不能表达它，也不证明恢复应当总在运输前**。

### 问题从哪里发生变化

传统赛题解答把订单货量视为输入，配送完成意味着将这些货量按时送达。在上述情境中，拣货执行本身才发现缺货；这次发现触发顾客决定；顾客回复又可能改变后续要做的工作。因而，开始执行订单时，全部拣货任务未必已经确定。

先限定一个门店、一名拣货员、一张已承诺订单和给定的交接截止时点，不先增加多仓、车辆路径、学习未知偏好等维度。以下是**待核实并建模的业务定义**，不是所有平台现行规则：

1. 顾客的预先授权和商品限制已知。需要额外确认的商品只在缺货被发现后发出替代请求；回复时延与选择可以相关，不能默认独立。
2. 等待回复时，拣货员可以继续处理其他商品；回复可以在其移动或拣货期间到达，并产生替换、撤下已拣商品等任务。
3. 企业连续选择下一项拣货/核查任务、何时发出可执行的请求，以及等待和返拣；是否能选择结束拣货的时点，须先核实实际权限。终止后的变更权限、未回复时的默认动作必须来自选定平台的真实规则，不能把沉默等同于同意。
4. 给定交接期限及明确授权边界，评价按顾客选择或预先授权规则完成的订单内容、缺失商品、返拣工作量和迟交。目标权重尚未确定，不凭空添加满意度罚价。

**候选研究问题：当缺货发现触发顾客确认、确认结果又生成或取消后续拣货任务时，如何组织这张订单的拣货与确认，使已经承诺的订单在截止前完成被允许的履约内容？**

这里有两个应分别定义的时点：最终交接期限 D，以及本次确认接口随订单离开 `picking` 而关闭的时点 C。D 不自动等于 C。C 若受企业行动影响，就属于政策的结果；若平台自动控制，则应作为给定的状态转移。不能先假设企业可以自由延长窗口，也不能在 C 之后继续把该接口的顾客回复当作可执行动作。

核心决策关系是“执行产生待决事项，待决事项的结果再改变执行”，且多个请求可以在后台同时等待。是否值得独立研究，取决于这一关系在现实中的重要性，以及既有拣货、调度和随机路径模型是否已完整处理它；不能只靠改一个名称立项。

### 最小时间线：为什么回复不能直接压成固定接受率

这是解析示意，不是企业数据、求解实验或算法优越性证明。设交接截止为第 7 分钟，顾客从请求发出到回复固定需要 3 分钟，回复后完成指定替换还需 2 分钟。第 1 分钟发现缺货并请求，则第 4 分钟收到回复、第 6 分钟完成；第 4 分钟才请求，则第 7 分钟回复、第 9 分钟完成。两种情况下顾客可以同样愿意接受该商品，但“回复后仍有时间执行”的条件不同。

一般地，若请求时点为 s、回复时延为 R，且该回复分支确定需要额外执行时间 τ，则本分支按时执行至少要求 s + R + τ ≤ D，其中 D 为截止时点。若 τ 取决于回复时拣货员的位置，则需要把位置和后续行动纳入判断，不能把 τ 当成统一常数。上述条件只针对需要先回复再执行的分支；有预先授权的动作另按真实规则处理。

它说明请求时点、回复内容和后续可执行性需要一起描述，**不证明这个数学结构本身新颖，也不支持“拣货越快越差”的无条件结论**。更早发现缺货反而可能增加有效确认时间。

### 一页问题定义草案

**问题（暂定）：一名拣货员执行一张已承诺订单时，缺货触发的顾客确认会在执行中新增或取消后续取货任务；确认结果异步到达，且只在订单仍处于拣货状态时可执行。如何安排取货顺序、请求时点、等待、返拣与结束拣货，使截止前可交付的商品与工作量达到给定目标？**

- **主体与范围**：先限定一个门店、一名拣货员、一张订单及给定截止时点 D；多订单共享库存、多拣货员和车辆路径暂不进入，避免一次加入无关维度。
- **对象与状态**：订单行（未拣、已找到、已提出替代、待回复、已同意、已拒绝、待退款）、替代品位置与接受概率、拣货员位置与已携带商品、待回复请求及已等待时长、是否仍在拣货状态。
- **信息顺序**：缺货只在到达货架时发现；请求在发现后发出；回复时延随机且可与顾客选择相关，不能默认独立；回复到达后才能执行相应取货；订单离开 `picking` 后接口关闭；交接期限 D 与窗口关闭时点 C 分开记录。
- **行动**：选择下一站；决定是否及何时发出请求、提出哪个替代；等待或继续其他取货；回复后返拣；在授权规则允许时退款、放弃或结束拣货（结束权限待核实）。
- **终止与评价**：截止前实际可交付的商品集合、缺失与退款、行走距离与工时、返拣次数、是否按时交接；不预置满意度罚价。
- **必要机制**：回复不是单纯延迟，而是生成或取消任务；窗口关闭使“回复是否仍来得及执行”成为独立判断；两者与空间移动耦合。

请求等待年龄也需要核对。设回复时延 R 的生存函数为 S(u)=P(R>u)，仅在 S(u)>0 时，已等待 u 仍无回复后再等待 Δ 的无回复概率为 S(u+Δ)/S(u)。这是一项普通条件概率恒等式，不是新理论；除非采用无记忆等特殊假设，不能只因两个请求都为 `PENDING` 就令其未来回复分布相同。没有数据时不选定分布，存在回复相关性时也不把该单项公式当成请求间独立的依据。

### 四项检查

**1. 删去行业名称后还剩什么。** 去掉生鲜、冷链、门店等词，问题是“带异步审批请求的拣货路径与任务生成”。缺货发现、替代确认和回复改变任务都不依赖商品易腐；若论文只保留这层结构，应按即时零售/电商履约定位，生鲜只在数据与场景说明中出现，不作为机制卖点。为突出生鲜而额外加入温控或腐败约束属于人为叠加，不进入定义。

**2. 冻结核心机制后，决策是否改变。**

| 冻结对象 | 退化后的问题 | 被去掉的决策 |
| --- | --- | --- |
| 回复生成/取消任务（替代在接单期确定） | 固定清单 + 随机等待/放弃/期限（Bhowmick 类） | 是否为尚未确定的替代保留时间与位置、请求时点如何与路线配合 |
| 窗口关闭（允许结束后继续执行，或 C=D 且不阻塞结账） | 只有期限约束的等待与路径 | 把结账时点当作关闭窗口的行动、为“回复是否来得及”调整顺序 |

两种冻结都改变可行行动集与评价结果，说明机制有决策后果；这不等于新颖，也不证明必须开发新算法。

**3. 判别实例（手算，非求解实验）。** 单拣货员，直线距离；O 为起点，A 为缺货商品货架（距 O 1 分钟），A′ 为替代品（距 A 1 分钟、距 O 2 分钟），B 为另一商品（距 O 10 分钟）；按“发现缺货后提出替代”的假设，请求只能在 A 发出，回复到达前不能取 A′；期限 D=12 分钟。

- R=1：t=1 在 A 发请求，t=2 收到回复；路线 A→A′→B 于 t=10 完成，A′ 与 B 都可交付。
- R=5：t=5 才收到回复；A→A′ 于 t=2 到达后等到 t=5，再去 B 为 t=13>12；先去 B（t=10）再回 A′ 为 t=18>12。硬期限下只能放弃 B 或放弃 A′。
- 若替代在接单期已确定（冻结第一项），两种 R 下都可按 A→A′→B 在 t=10 完成，R 不影响可行性。

同一路线、同一期限，仅因回复时延与“回复到达才能取”就改变了可交付集合；把回复时延写成常数、把接受率写成外生概率而不表示任务生成，仍会漏掉条件可执行性对可行集合的影响。该例是解析构造，不含随机分布或企业数据，只用于检查定义是否遗漏决策关系，不证明文献空白。

再检查窗口：若结账不得晚于 C=9，且结账后未决请求不能执行，则 R=1 下 t=10 完成的路线不可行，只能在 t=9 前结账并放弃 B，或放弃 A′ 后提前完成；若 C=D=12，两项都可交付。C 与 D 不自动相等，具体规则仍待平台证据；该例只说明 C 必须单独核实，不能把剩余配送时间当作剩余回复时间。

### 当前判断与进入建模的条件

执行中重优化（Lorenz 等）、随机等待/放弃/期限（Bhowmick 等）、自挂起恢复（Chen 等）、替代建议与替代—路径联动（Laporte 等；专利）分别已覆盖；“回复生成/取消任务 + 窗口关闭”为差异待检验；未回复默认动作、结束权限、回复时延与 C 为证据不足。

据此不撤回候选，也不立项：完整关系未被已读文献覆盖，但业务参数缺失，且机制不属于生鲜冷链特有。进入建模至少需要两项证据：平台规则或访谈/日志支持“回复改变任务、结账关闭窗口、存在未回复处理规则”；判别实例扩展到更广实例后，完整机制与冻结模型的策略仍有稳定差异。二者缺一，就把候选停在“差异待检验”，不以推测补参数。

### 下一步按顺序做什么

1. 业务证据：未回复默认动作、结束拣货权限、C 的实际规则、回复与返拣时间。官方文档没有；需平台规则、访谈或日志。拿不到就停止，不以教程示例外推，也不把沉默当作同意或拒绝。
2. 文献：取得 D'Haen 等全文，核对执行中订单修改是否已覆盖任务生成；追查随机调度中的信息请求时点与订单修改/返工两条线；只把读到的正文写进对照表，未读到的标“尚未读到”。
3. 参数与差异都成立后，建最小 MDP，用 `run.py --purpose` 留证；比较完整机制、冻结任务生成、冻结窗口三种设置，并用精确枚举核对小实例。所有方案放回相同授权规则、窗口和期限下评价。
4. 差异稳定后再选经典算法并设计针对性部件；否则回到候选发现，不把该问题改写成算法练习。

## 降级候选：共享履约记录迟到时的生鲜库存分配

**当前决定：暂停作为新问题主线，不进入建模。** 进一步核查发现，候选此前强调的共享记录、多条件齐备和根据核查结果继续行动，都有相近的成熟问题结构。确定性核心可以直接写成前置任务调度。完整随机库存/配送联合问题是否已有完全相同定义尚未查清，但目前没有足够现实与文献证据支持为它单独立项。

### 现实入口及证据边界

货物已到库、尚未过期，并不必然代表它已经具备向指定客户交付的条件。接收方可能要求覆盖运输过程的温控记录；缺失记录可能导致拒收。

- **买方条款证据**：[Din Hau Asia Food 的交货指南](https://7cca475f-d816-4cfa-b9ad-9e59e85410d9.filesusr.com/ugd/2cd7e3_ee89ca403485422c91203896649ddfe5.pdf) 第 14—15 条要求提供运输温度记录，并约定记录缺失或温度无法证明时可拒收。该文件是特定企业的合同条款，不代表全部企业、全部货品或普遍法律规则。
- **原始实证研究**：[Waldhans 等（2024）](https://doi.org/10.1007/s41783-024-00165-2) 调查了 45 家、主要在德国的企业；其中 40% 的受访者只在请求或投诉时交换温度监测数据。它支持记录跨主体传递不充分的现实动机，不证明本文候选中的共享依赖、可控制的催取时间或拒收发生率。

“一份记录关联多批货、每批货需要多份记录、补齐顺序能影响履约”是以下候选的关键机制，**尚未在本项目数据或企业事件中确认**。原始订单表没有这些字段，不能把这一情境说成已在赛题企业观察到。

补充查到马来西亚 NPRA 的 [VAR/PPAR 填写说明](https://npra.gov.my/images/Industry/inspection/coldchain/GuidelinesforcompletingtheVARPPAR.pdf)：同一疫苗/血浆产品的一票货物包含多个批次时，使用一份报告；报告包含运输冷链与逐批次信息。已读取该两页文件，版本为 2018 年 4 月 1 日生效的 v02.2018。这支持相邻冷链行业中“多批次共享一份报告”的存在，不证明它在生鲜企业中的发生方式，也不证明催取可控、记录迟到频率或其优化价值；不将历史文件表述为当前通用法律要求。

### 决策情境

一家生鲜配送企业有若干在库批次和待履约订单。企业掌握每批货已知的品质状态、剩余可用时间及现有记录；部分真实记录由上游、运输方或仓储方保管，尚未到达。记录获取耗时、有资源限制，并可能揭示货物实际不合格。不同批次可能依赖同一段运输记录；一个批次也可能同时依赖多个交接段的记录。

企业需要在订单截止前，连续决定：先催取和核查哪些记录、哪些批次继续等待、哪些订单由已满足条件的批次替换，以及何时承诺或停止承诺交付。等待会消耗货物剩余可用时间，替换又会占用其他订单的库存与运力。接收与放行遵守真实合同及质量要求，不能用预测出的温控历史代替缺失记录，也不假设获取记录一定能使货物合格。

**候选问题表述：在批次共享履约记录、记录获取结果与到达时间尚未确定的生鲜网络中，如何联合决定记录获取顺序与库存分配，使订单在品质、记录和交付期限三方面同时满足要求？**

### 原候选试图保留的关系

单独给每批货标注一个“预计可发货时间”，可能丢掉获取顺序带来的相互影响。例如，批次 A 需记录 r1、r2，批次 B 需 r1、r3。取回 r1 不一定使任一批次立即可发；它随后对哪批货有用，取决于 r2、r3 是否齐备及相应订单的期限。该例只说明拟研究的依赖关系，不是项目实测事件，也不证明这一数学结构首次被研究。

需要核查的核心是：实际库存的可交付范围是否由获取和核查记录的行动共同决定，且这种影响跨批次、跨订单传播。记录获取、库存替换和承诺时点须在同一决策过程中权衡。

### 确定性核心的结构对照

以下是本项目的解析对照，不是文献原定理，也没有运行求解实验。限定每条记录的获取/核查时长已知、记录需求关系固定、结果均合格且取得后持续有效；不包含随机结果或记录撤销。

把记录 r 的获取/核查记作任务，完成时间为 Cᵣ。批次 b 的物理可用时点为 aᵦ，所需记录集合为 Rᵦ，则最早具备记录条件的时点为：

\[
T_b=\max\left(\{a_b\}\cup\{C_r:r\in R_b\}\right).
\]

这正好对应一个“批次可发货”里程碑：它等待物理到货及全部所需记录任务完成。同一 Cᵣ 可成为多个批次里程碑的前置条件，已经表达记录共享；取回 r1 尚不足以放行、还要等待 r2 的情形，就是合取前置关系。人员/接口占用对应可再生资源限制，交付期限与剩余可用时间对应后续任务的截止限制。

因此，候选此前给出的 r1/r2/r3 例子只能说明为什么要联合考虑前置任务，**不能说明发现了新的问题结构**。这项对应不证明完整随机候选与某篇已有论文完全等价；它足以撤回把“共享记录解锁库存”本身作为新颖性依据的说法。也不通过给一般数学规划增加变量就推断任何业务问题都已被研究。

### 降级理由和重新启动条件

当前有证据的是部分行业的记录要求及报告共享。仍缺少生鲜场景下记录获取的可控行动、真实时间线及跨订单后果。把普通排程的任务改名为记录，再附加常规库存和时效约束，目前不足以优先立项。

后续可在补齐生鲜业务依据后，沿已有机制继续细查最接近模型与尚未核查的具体关系，不要求先另造一个新机制才能重新评估。随机性、客户差异、多个仓库等细节需要核查其现实作用、已有覆盖与决策后果，既不自动确立贡献，也不自动视为无意义叠加。暂停主要基于业务依据缺失和研究优先级，不意味着完整联合问题已被证明没有研究空间。

## 如重新评估，立项前仍需补齐的证据

1. 找到可核查的事件或流程材料：同一运输/交接记录确实影响多个批次；记录缺失影响接收；可采取的获取行动确实改变记录到达过程。任一核心机制不成立时，缩减或淘汰候选。
2. 提取事件时间线：批次物理到达、记录请求与返回、核查结果、允许放行、订单承诺、实际接收、过期/退货。分别记录物理状态、信息状态和接收条件，不把未知品质当作合格。
3. 深读最接近的批次放行、易腐库存、共享前置任务和信息获取模型，逐项核对其主体、信息、动作、状态和完成条件。不能仅依据关键词检索结果宣布空白。
4. 只有机制及问题差异得到支持后，才构造最小实例比较联合决策与先补记录/先分配库存等流程。目的首先是判断新决策关系是否产生不可忽略的影响，不能用人为参数制造优势。任何计算均通过 `run.py` 留证。
5. 确认研究问题后，再讨论可证明的性质、算法和实验数据；可继续使用赛题地理网络作背景，但补充批次与记录数据的来源必须单独说明。
